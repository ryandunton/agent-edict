AI coding agents act on your machines. Who sets their limits?

Claude Code, Codex, Copilot and the rest run commands and change files with the developer’s own access. Every vendor offers admin controls, but each in its own place, so there’s no single baseline to set.

What they can do

Run shell commands, edit files, read SSH keys and cloud credentials, and call outside tools over MCP. Most have a mode that approves everything.

Who decides today

Each developer, in their own settings. Safeguards can be switched off, and every new agent arrives without them.

Ten tools, ten formats

A different file, format and path for each tool on macOS, Linux and Windows. Some controls exist only in a vendor console, often on a business plan.

10 tools · 4 ways policy is delivered: system files, MDM profiles, vendor consoles and per-user hooks · 3 operating systems

One rule, “never run sudo”, as four of the tools need it on Linux:

Claude Code/etc/claude-code/managed-settings.json
"deny": [
  "Bash(sudo:*)"
]
Codex/etc/codex/requirements.toml
[[rules.prefix_rules]]
pattern = [{ token = "sudo" }]
decision = "forbidden"
GitHub Copilot/etc/github-copilot/managed-settings.json
"deny": [
  "Shell(sudo *)"
]
Kiro/etc/kiro/managed-settings.json
{
  "capability": "shell",
  "match": [
    "sudo *"
  ],
  "effect": "deny"
}

Write it once. Ship it everywhere.

Your policies go in. Signed, validated, native controls for every client come out.

1Define

Choose who gets what

Set a standard policy, plus group rules where people need something different. Each machine applies the policy for whoever is logged in. On a shared machine, the higher-ranked one covers everyone.

policy-map.yaml
2Compile

Generate native controls

AgentEdict writes each client’s own settings and hooks. If a client can’t honor a constraint, compilation fails instead of weakening it.

edict compile-bundle
3Ship

Validate, sign, install

Check the bundle’s scope and artifacts, sign the release, and verify the signature before anything touches the endpoint.

edict validate-bundle

    Guardrails, not a sandbox.
    
          
    AgentEdict distributes and verifies local policy. What each AI tool enforces still depends on that tool and on how the endpoint is protected. Here’s exactly where the line is.
    
        
    
        
    
          
    
            
    What you get
    
            
      
              
    • One signed bundle. Each agent gets the policy for whoever is logged in, applied machine-wide.
      • 
              
    • Bundle validation of declared scope, required artifacts, and formats.
      • 
              
    • Protected files and hooks that reduce accidental use of unapproved tools.
      • 
            
    
          
    
          
    
            
    What it doesn’t claim
    
            
      
              
    • Protection from local administrators or root, who can change or disable controls.
      • 
              
    • Proof that a running client loaded its files or calls its hooks. That needs endpoint verification.
      • 
              
    • OS containment of its own. Where a client has a sandbox, the client enforces it.
      • 
              
    • Per-user isolation. On a shared machine, one policy per agent covers everyone logged in.
      •

    # Build the CLI
mkdir -p bin dist/native/profiles
go build -o bin/edict ./cmd/edict

# Compile and validate the native example
./bin/edict compile-native \
  -profile examples/native/local-guardrails.yaml \
  -target-os all -output-dir dist/native/profiles
cp examples/native/policy-map.yaml dist/native/policy-map.yaml
./bin/edict validate-bundle \
  -dir dist/native -target-os all
